# Clue & Puzzle-List Curation — Spec

Deferred follow-up to the no-lose restructure. Goal: reduce frustration from
obscure clues (mainly "names of people from decades ago") **without** shrinking
the puzzle pool or breaking chains.

## Why this is now a polish lever (not urgent)

The game is no-lose: an obscure clue no longer ends a run — you fail that one
level (it shows 🟥 "given" and reveals the answer) and keep going. So clue
quality now affects **flawless rate and satisfaction**, not whether a player can
finish. That argues for the cheapest, lowest-blast-radius fixes first, and against
anything that reshuffles live daily puzzles.

## How clues & puzzles resolve today (the constraints)

- **Weekday arrays** `src/app/clues/<day>.ts` — entries `["num","clue","ANSWER"]`,
  large supersets that also include non-5-letter answers.
- **Clue lookup** `buildClueMaps()` (`src/app/game/game.component.ts:241`) —
  answer → clue map, **first occurrence in the file wins**.
- **Puzzle pool** `src/app/clues/chains.ts` — **2024 pre-built, word-disjoint
  chains** (each answer unique across the whole set), generated by
  `src/tools/generate-chains.mjs` from the de-duped 5-letter answers per day
  (also first-occurrence). `setChain()` maps a day to a chain via
  `(puzzleNumber - 1) % 2024`.

**Two independent levers fall out of this:**

| Change | Regen needed? | Pool impact | Blast radius |
|---|---|---|---|
| Change which **clue text** shows for an answer | No | None (answer stays) | Deploy-safe — dailies unchanged |
| Remove an **answer** entirely | Yes (`generate-chains.mjs`) | Shrinks / reshuffles | High — **reshuffles every daily** and changes chain count |

Because clue resolution happens at runtime by first-occurrence, curating *clue
text* never touches `chains.ts`. Removing *answers* re-runs the deterministic
greedy generator, which changes the whole `(n-1) % len` mapping — i.e. every
player's puzzle #N becomes a different puzzle, mid-streak. Avoid unless necessary.

## Levers, in priority order

1. **Clue override map (recommended primary).** Add
   `src/app/clues/clue-overrides.ts` — `Record<ANSWER, { clueNumber: number; clue: string }>`
   — and check it first in `buildClueMaps` before falling back to the weekday
   array. Hand-authored or auto-filled. Fixes both "fine answer, bad clue" and
   "sole-obscure clue" cases with **zero regen, zero pool loss**, and a tiny,
   reviewable diff kept out of the giant generated arrays.
2. **In-file reorder / prune.** When an answer already has a better alternate
   clue lower in its weekday file, delete the bad first entry (or move a better
   one above it) so first-occurrence improves. Same deploy-safe properties;
   scriptable.
3. **Answer denylist + regen (last resort, batched).** For genuinely bad
   *answers* (obscure answer, not just clue). Add to a denylist consumed by
   `loadPool` in `generate-chains.mjs`, then regenerate. ⚠️ Reshuffles all
   dailies and changes the count — do only as a rare, deliberate content release,
   and consider first making the generator **stable** (preserve existing chains,
   replace only affected ones) so streaks/history survive.

## Phase plan

### Phase 0 — Analyzer / triage tool  (`src/tools/analyze-clues.mjs`)
- **Parse the arrays reliably.** Import or `eval` the array literals — do **not**
  scrape clue text with a loose regex. (A quick regex pass during planning threw
  false positives: 8 Thursday answers flagged as "no clue" that in fact resolve
  fine at runtime, e.g. `PIXAR`, `JANET`.) Reuse the answer-anchored regex from
  `generate-chains.mjs` (`loadPool`) for answers, and load full triples by
  evaluating the array.
- For all 2024 × 7 shown clues: resolve the first-occurrence clue, compute an
  **obscurity score**, and record whether a cleaner alternate clue exists for
  that answer.
- Emit a ranked report (CSV/JSON, worst first) + alternate availability — the
  human triage list that drives Phase 1.
- **Obscurity signals (tunable):** person-role words (actor/composer/singer/…),
  a year or decade, "of old / of yore / once", foreign-language markers,
  abbreviation-style clues. **De-weight** quoted *short phrases* (`"Me too"`) —
  they read as titles but aren't obscure. Useful positive signal: the same answer
  also appears in an easier day (Mon/Tue) with a plainer clue → a good alternate
  almost certainly exists.
- Baseline from planning (approximate, pre-de-noising): ~5% of shown clues are
  genuine person/dated-name clues; the headline "16%" is inflated by quoted
  phrases. Treat these as order-of-magnitude until the analyzer parses cleanly.

### Phase 1 — Curate via overrides / reorder  (Levers 1–2, no regen)
- Extend `buildClueMaps` to consult `clue-overrides.ts` first.
- Auto-fill overrides from the analyzer where a strictly-better alternate exists;
  hand-author overrides for sole-obscure answers.
- Review the diff, ship. Deploy-safe (no daily reshuffle).

### Phase 2 — Answer pruning + regen  (optional, only if Phase 1 leaves bad *answers*)
- Denylist + `generate-chains.mjs` regen; batched, deliberate release.
- Prefer a stable generator variant first (preserve existing chains).

### Phase 3 — Feedback loop  (ongoing)
- Wire the existing "provide feedback" link (`about.component.html`) into a
  lightweight workflow that appends reported answers/clues to the override map or
  denylist.

## Verification
- **Analyzer:** parse count must match the array sizes (no false "missing");
  hand-check a sample of the top-ranked obscure clues.
- **Overrides:** unit test that `buildClueMaps` returns the override when present;
  run the app on a level whose answer is overridden and confirm the new clue shows.
- **Regen (if Phase 2):** `node src/tools/generate-chains.mjs`; confirm chain
  count is ~stable; `npm test` (the chain-integrity spec validates 5-letter /
  linking / no-repeat) and `npm run lint`.
